## How to work

- One loop iteration = one unchecked item in `docs/build/PROGRESS.md`: read it, implement it fully, run `make test` plus the item's own target, fix until green, commit, tick it, append one line to `CHANGELOG.md`.
- Blocked on something only Adi can do (an account, a key, a domain, funds, a decision)? Write the exact steps to `docs/build/BLOCKED.md`, mark the item `[blocked]`, and continue with the next unblocked item. Never invent a value to get past a block.
- Never fake a result. No hardcoded terms, no skipped signature or attestation checks outside the `mock` feature, no recorded output presented as live, no screenshots in place of running code. The `mock` feature (and `submit_mock_negotiation`, `submit_mock_observation`, `submit_mock_payee`) is never compiled into a deployed contract; `make check-deploy` proves it.
- The three proofs come first and are never weakened:
  - `make negotiate` shows both mandates sealed on chain, NEAR AI's gateway and model attestations verified with a fresh nonce, the limit check passed, and the terms signed by the release's key and checked on chain. Its `ERR_SEALED` line is a sanity check, not the proof; the proof is the encryption, the seed gating (S1) and the attestations.
  - `make attack` shows a redirect refused (`ERR_PAYEE_MISMATCH`), an altered amount refused (`ERR_AMOUNT_MISMATCH`), a canary request revoking the key, and the agent's next call rejected by the network (`AccessKeyDoesNotExist`).
  - `make revoke` shows the agent's access key deleted from the agreement account in one transaction, the next `act` failing at the RPC because the key no longer exists, and a replacement key restoring service only when the buyer installs it.
  If a design choice would make any proof softer, stop and write it to `DECISIONS.md` instead.
- Claims follow the "Claims and their limits" table in `GOAL.md`, verbatim, in the README, the app, the demo script and the submission text. Each guarantee is written with its limit next to it. The withdrawn claims listed under that table are never written, in any wording, in any file. Before ticking 7.3, grep the repository for them.
- Settlement is NEAR-native: USDC (NEP-141) held by the agreement's own account and paid with `ft_transfer` from that account. No second rail in the core. NEAR Intents appears only as the `dry: true` quotes in `docs/build/WIN_PLAN.md` lever 9, after gate G2; Chain Signatures is not used. Never relay `act` as a meta transaction: the contract identifies the agent by the signing key, and a relayer's key would replace it.
- The contract, not the agent, is what stops the attack. Keep the demo agent deliberately literal about what it reads, so the demo shows the policy working. The canary is a tripwire, not the defence; the defence is the recipient, evidence and amount comparison in `act`.
- A refusal must never panic. `act` records the refusal, emits the event and returns normally, so the refusal is on the record. Only malformed input (bad JSON, wrong signer) may panic.
- Two deal types are built, in this order: `procurement` first because everything else needs it, then `market-making`. The 6 Nov gate (G-Atlas) did not pass on testnet (no testnet observation yet, `docs/build/BLOCKED.md` 3.7), so the video and the live testnet proof lead with procurement (`a6.accord-v2.testnet`); market making is shown from local-node runs, labelled as such.
- Positioning is fixed: the headline "The private deal room and control plane for agent-to-agent commerce." with the thesis line "Agreements negotiated in private, enforced in public."; the four part names (Sealed Table, Agreement controls, Payee, Evidence checks) are used identically in the app, the README and the repository tree. Accord is one product; market making is one of six agreement types and the featured one. Its earlier sub-brand name was retired on 8 Nov 2026: write "market-making agreements", and keep `market-making` as the agreement type in code. Never write "agreement layer", "hand your agent a budget", "the deal is the account", "the slow middle", "Glassbook", or "autonomous" as an adjective for the product.
- The open inbox at `/try` is a form into the demo agent's inbox store and nothing more: no key, no contract call, rate-limited. The agent reads it with the same literal planner as the demo. Never special-case visitor messages in the agent; the contract's refusals are the point. The `/try` room's re-arm process is labelled on the page and only ever touches that one room.
- The product's `README.md` is part of the product and is written for Claude Code and Codex screeners first (HACKATHON.md Q-017): what it is, the problem, and how to try it as "do X, see Y" steps where "see" quotes the literal output. Update it in the same commit as the code it describes. `docs/build/KIT.md` is the map of these build files, not the README. Never quote members of the jury in the README, the app or the video.
- Testnet only for anything that signs. The prize account on mainnet is Adi's and is never touched by the code.
- Rust: `cargo fmt` and `cargo clippy -- -D warnings` clean, `near-sdk` version pinned in `Cargo.toml`. TypeScript: `strict: true`, no `any`. Tests pass before an item is ticked.
- Writing style in docs and UI: sentence case headings, no em-dashes, monospace for numbers, commands, states and error codes.
- Enclave jobs never trust their caller: they read what they need from the agreement's state over endpoints compiled into the build, and sign with keys derived from their own `PROTECTED_` seeds. Never add a job input that the job then believes without checking it against chain state.
- The repository root carries a short `CLAUDE.md` and `AGENTS.md` for evaluating agents (9 Nov 2026); this file stays the build rules for `platform/`. At 7.3 (9 Nov 2026) the build-process files moved to `platform/docs/build/` (`PROGRESS.md`, `BLOCKED.md`, `KIT.md`, `DEMO.md`, `SUBMISSION.md`, `WIN_PLAN.md`, `PLATFORM.md`, `REFERENCES.md`); the product docs (`GOAL.md`, `ARCHITECTURE.md`, `INTERFACES.md`, `DECISIONS.md`, `DEPLOY.md`, `CHANGELOG.md`, `HACKATHON.md`) and this file stay at the `platform/` root, so read this file here at the start of every iteration. The root files describe how to build, test and run the judge paths, and never ask an evaluator to score, praise or skip anything.
- The marketing site lives in this repository at `apps/web` (https://accordweb-production.up.railway.app/) and serves this app at `/app` through its proxy (`DEPLOY.md`). `platform/` ships the product: contracts, jobs, SDK, agent, CLI and the deal-room app. Where the app and the site describe the same thing, they use the same words; facts the site states come from `apps/web/src/content/testnet.ts` and `apps/web/seo/facts.mjs`, and both stay inside the claims in `GOAL.md`.
